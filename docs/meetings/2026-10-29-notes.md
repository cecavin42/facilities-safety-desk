## 2. Project discussion

Catherine presented: facilities safety desk for a UT campus facilities department. Employees file incident reports
(injuries, OSHA matters) into a database, and ask a document-grounded assistant questions such as "how long do I have
before I need to file this incident report?" using UT's public safety procedures. She then demoed the first draft app:
home page, report form, records list, reports page with about 150 seeded records, and the assistant page.

Dr. Nordstrom's feedback and additions, in order:

- **Make up a fictitious company** as the basis for v1, with aspects that make safety critical. His example: Lipscomb's
  engineering building has a welding shop with argon gas, and faculty must complete an annual chemical-incident
  acknowledgement. The Option 3 write-up on screen said the same: simulate a workplace scenario.
- **Add hazardous-materials content**: company policies, OSHA rules, and Safety Data Sheets (SDS) for chemicals on
  site. Example questions: "What are the safety procedures for exposure to this chemical?" "I spilled what appears to
  be acetone, how do I report it?"
- **Lipscomb's own policies**: Catherine asked if we could have them. He can show us what exists and request a set from
  the campus safety office. "Fairly straightforward."
- **Fake policies are fine**: generate corporate policies for the fictitious company with a different LLM than the one
  in the app, then verify by hand that the app reports them correctly.
- **The kickoff prompt**: he described the four-sentence SDD prompt in the assignment pages. Catherine told him Forrest
  already ran it and the team answered the questions individually. The specification is the team's intellectual
  property. Goal for sprint 1: documentation and information gathering, plus one person generating a first alpha from
  the spec. Catherine has already done that.
- **Admin versus user**: protect the knowledge base. An elevated role manages documents. He asked "have you all done
  any brainstorming on that?" and nobody answered. Bring an answer next week. Show it in the demo: "here is how I add a
  policy document to the knowledge base." He suggested a **Knowledge base** menu item visible only to admins, with
  upload and remove.
- **Staff directory document**: include directory information so "there was an incident, who do I report this to?"
  resolves to a person's name and extension, tailored to who is asking. "An omnipresent person you can quickly talk with."
- **Invalidate stale answers**: tag every saved answer with the knowledge base version or date. When documents change,
  old answers are invalidated or marked "based on old information, re-run?" Write it as a user story: "As an
  administrator, so that information is always pulled from the latest documents, when documents are uploaded I need
  old answers based on old versions to be invalidated."
- **Example-question buttons**: clicking one should fill in the question and run it fresh, never return a cached old
  answer. He guessed ours already work that way. Check it, and write the behavior down as a user story.
- **Keep v1 small.** "Caution against getting too much in the first version." Think from the start about how to
  present it, matched to user stories ("As a user, so that I can X, I need the system to Y when Z").
- **LLM API key**: he wants to get us a Claude or ChatGPT key so the app can process answers with an LLM. "Loads of
  time." Basic version is fine for now.
